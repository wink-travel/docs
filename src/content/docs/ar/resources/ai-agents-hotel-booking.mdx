## التوصية بفندق ليست حجزًا له

معظم "السفر بالذكاء الاصطناعي" اليوم يتوقف عند التوصية. يقترح المساعد ثلاثة فنادق، ثم يحيل المسافر إلى موقع ويب أو وكالة سفر عبر الإنترنت لإتمام الحجز فعليًا. ينقطع الخيط، قد لا يكون السعر قابلًا للحجز، ولا يحتفظ أحد بسياق المصدر.

**وكيل الذكاء الاصطناعي** يختلف عن إجابة الذكاء الاصطناعي. الوكيل لا يصف الفندق فقط — بل يتصرف: يتحقق من التوافر الحي، يجمع الحجز، يأخذ الدفع، ويمكنه التفاعل عند حدوث تغييرات. لكي يحدث ذلك بأمان، يحتاج الوكيل إلى أكثر من نص. يحتاج إلى بيانات منظمة، حالية وقابلة للحجز وطبقة معاملات يمكنه استدعاؤها.

هذا هو الفرق بين [اكتشاف الذكاء الاصطناعي](/ar/resources/ai-discovery-hotels/)، الذي يتعلق بأن تكون **مكتشفًا ومفهومًا**، والتجارة الوكيلة، التي تتعلق بأن تكون **مُنجزة**.

## ما يحتاجه الوكيل قبل أن يتمكن من إجراء المعاملة

حجز الفندق هو حدث تجاري حقيقي: الغرفة المناسبة، السعر المناسب، التوافر الحقيقي، السياسات، الدفع وتأكيد يتزامن مع الفندق. لا يمكن للوكيل إتمام ذلك إلا إذا كانت كل قطعة متاحة كعملية قابلة للاستدعاء.

| ما يحتاجه الوكيل | لماذا هو مهم |
|---|---|
| عرض منظم وحيوي | البيانات المجمعة من الويب تصبح قديمة؛ يحتاج الوكيل إلى مخزون حالي يتحكم به الفندق. |
| أسعار وتوافر في الوقت الحقيقي | يجب أن يكون السعر الذي يقتبسه الوكيل قابلًا للحجز فعليًا في تلك اللحظة. |
| عملية حجز | يجب أن يكون إنشاء الحجز استدعاء API حقيقي، وليس إحالة إلى نموذج ويب. |
| الدفع | يجب أن يكون الوكيل (أو المسافر من خلاله) قادرًا على الدفع، مع تطبيق منطق السياسات. |
| النسبة | يجب أن يبقى المصدر، الحملة أو الوكيل الذي أنشأ الحجز مرتبطًا. |
| الأحداث | يجب أن يكون الوكيل قادرًا على التفاعل مع التأكيدات، التغييرات، الإلغاءات والاستردادات. |

بدون هذه، يمكن للوكيل التوصية — لكنه لا يمكنه الحجز.

## كيف يحجز وكيل الذكاء الاصطناعي فندقًا على Wink

Wink يعتمد على API أولاً: كل ميزة في المنصة قابلة للاستدعاء خارجيًا، ويكشف خادم MCP المستضاف عن عقود API الحية للوكلاء. تدفق وكيل نموذجي:

### 1 — الاتصال وقراءة العقود الحية

يتصل الوكيل بخادم MCP المستضاف ويستخدم `api_search` و `docs_search` للعثور على العمليات الصحيحة وقراءة مخططات الطلب/الاستجابة الحقيقية — لا تخمين لنقاط النهاية، ولا وثائق قديمة.

```bash
claude mcp add --transport http \
  wink-docs https://docs.mcp.wink.travel/mcp
```

### 2 — البحث في المخزون القابل للحجز

يبحث الوكيل في العرض الذي يتحكم به الفندق، بما في ذلك البحث المكاني الجغرافي، ويقرأ الأسعار الحية والتوافر عبر مديري القنوات المتصلين.

### 3 — إنشاء الحجز

إنشاء الحجز هو عملية REST API. يجمع الوكيل الغرفة، السعر، التواريخ والضيوف، وينشئ الحجز عبر API.

### 4 — أخذ الدفع والتأكيد

يقوم [Booking Engine](/ar/products/booking-engine/) بتنفيذ المعاملة — الدفع، الدفع (Wink هو التاجر المسجل)، منطق سياسة الإلغاء، التأكيد، ومزامنة الحجز مع نظام إدارة الممتلكات المتصل أو مدير القناة. يتم الحفاظ على المصدر والنسبة عبر الحجز.

### 5 — التفاعل مع الأحداث

يمكن للوكيل الاشتراك في `booking.created` وأحداث webhook الأخرى للمصالحة، إعلام المسافر، أو تفعيل إجراءات متابعة.

المبدأ: **الوكيل ينشئ أو يوجه النية؛ يظل Booking Engine طبقة التنفيذ تحت كل إحالة.**

## البحث بالذكاء الاصطناعي مقابل وكلاء الذكاء الاصطناعي

يؤدي كل منهما وظائف مختلفة، ويحتاج الفندق إلى الاستعداد لكليهما.

| | محركات البحث / الإجابة بالذكاء الاصطناعي | وكلاء الذكاء الاصطناعي |
|---|---|---|
| هدف المسافر | العثور على الفنادق ومقارنتها | الحجز وإدارة الإقامة |
| ما يحتاجه الفندق | [محتوى منظم وقابل للزحف](/ar/resources/hotel-content-answer-engines/) | API حي، أسعار، حجز، دفع |
| الحالة النهائية | توصية | حجز مؤكد |
| واجهة Wink | عرض نظيف + محتوى جاهز للإجابة | REST API، خادم MCP، Booking Engine |

يغطي [اكتشاف الذكاء الاصطناعي للفنادق](/ar/resources/ai-discovery-hotels/) جانب البحث؛ هذا الدليل يغطي جانب المعاملة.

## من يبني الوكلاء على التجارة الفندقية

التجارة السياحية الوكيلة ليست فقط مساعدين للمستهلكين. نفس البنية التحتية تدعم:

- **مساعدي السفر للمستهلكين** الذين يبحثون، يحجزون ويديرون الإقامة من البداية للنهاية.
- **وكلاء البنوك، الولاء والتطبيقات الشاملة** الذين يدمجون حجز الفنادق داخل تجربة العميل القائمة.
- **أتمتة الشركاء والمبدعين** التي تكتشف الفنادق المؤهلة، تبني الأصول وتحافظ على النسبة متصلة — مع كسب عمولة افتراضية 10% على الحجوزات المؤكدة.
- **مساعدي الفندق الجانبيين** الذين يساعدون الفرق على إنشاء المحتوى وتحليل الأداء عبر [Extranet](/ar/products/extranet/)، [Social](/ar/products/social/) و [Studio](/ar/products/studio/)، بينما يحتفظ الفندق بالقواعد.

## إلى أين يتجه هذا

القدرات أعلاه متاحة اليوم عبر REST API وخادم MCP. الاتجاه هو نحو تجارة أعمق موجهة بالوكلاء: بدائيات حجز أغنى موجهة للوكيل، هوية الوكيل وتفويضه لإجراء المعاملات نيابة عن المسافر، ومشاركة الوكلاء كمصادر مكتسبة ومنسوبة في شبكة الشركاء. الخط المشترك هو ثابت — **بنية تحتية للتجارة السياحية لوكلاء الذكاء الاصطناعي**، مع تنفيذ Booking Engine في الأسفل.

## الأخطاء الشائعة

- **معاملة اكتشاف الذكاء الاصطناعي ووكلاء الذكاء الاصطناعي كمشروع واحد.** أحدهما محتوى وبنية؛ والآخر API وتنفيذ. تحتاج إلى كلاهما.
- **السماح للوكلاء باقتباس أسعار لا يمكنهم حجزها.** يجب أن تأتي الاقتباسات من الأسعار والتوافر الحي، وليس من صفحات مجمعة.
- **فقدان النسبة عند الإحالة.** إذا أنشأ الوكيل الطلب، يجب أن يبقى الحجز مرتبطًا بذلك المصدر.
- **تخطي طبقة التنفيذ.** الإجابة ليست حجزًا حتى يحدث الدفع والتأكيد فعليًا.
