## Рекомендувати готель — це не те саме, що його бронювати

Більшість «AI туризму» сьогодні зупиняється на рекомендації. Асистент пропонує три готелі, а потім передає мандрівника на сайт або OTA для фактичного бронювання. Ланцюжок переривається, ціна може бути недоступною для бронювання, і ніхто не зберігає контекст джерела.

**AI агент** відрізняється від AI відповіді. Агент не просто описує готель — він діє: перевіряє актуальну наявність, формує бронювання, приймає оплату і може реагувати на зміни. Для цього агенту потрібні не лише тексти. Потрібні структуровані, актуальні, доступні для бронювання дані та шар транзакцій, який він може викликати.

Це різниця між [AI відкриттям](/uk/resources/ai-discovery-hotels/), що про **знаходження та розуміння**, і агентським комерційним сервісом, що про **здійснення транзакції**.

## Що потрібно агенту перед транзакцією

Бронювання готелю — це реальна комерційна подія: правильний номер, правильний тариф, реальна наявність, політики, оплата та підтвердження, що синхронізується з готелем. Агент може завершити це лише якщо кожен елемент доступний як викликана операція.

| Що потрібно агенту | Чому це важливо |
|---|---|
| Структуроване, живе постачання | Дані, зібрані веб-скрапінгом, швидко застарівають; агенту потрібен актуальний інвентар, контрольований готелем. |
| Актуальні тарифи та наявність | Ціна, яку агент називає, має бути реальною для бронювання в цей момент. |
| Операція бронювання | Створення резервації має бути реальним викликом API, а не передачею на веб-форму. |
| Оплата | Агент (або мандрівник через нього) має мати змогу оплатити з урахуванням політик. |
| Атрибуція | Джерело, кампанія або агент, що створив бронювання, мають залишатися прив’язаними. |
| Події | Агент має мати змогу реагувати на підтвердження, зміни, скасування та повернення коштів. |

Без цього агент може рекомендувати — але не бронювати.

## Як AI агент бронює готель на Wink

Wink — це API-перший сервіс: кожна функція платформи доступна зовнішньо, а хостинговий MCP сервер надає живі API контракти агентам. Типовий потік агента:

### 1 — Підключення та читання живих контрактів

Агент підключається до хостингового MCP сервера і використовує `api_search` та `docs_search`, щоб знайти потрібні операції та прочитати їхні реальні схеми запитів/відповідей — без здогадок щодо кінцевих точок, без застарілої документації.

```bash
claude mcp add --transport http \
  wink-docs https://docs.mcp.wink.travel/mcp
```

### 2 — Пошук доступного для бронювання інвентарю

Агент шукає постачання, контрольоване готелем, включно з геолокаційним просторовим пошуком, і читає живі тарифи та наявність через підключені channel manager.

### 3 — Створення бронювання

Створення бронювання — це операція REST API. Агент формує номер, тариф, дати та гостей і створює резервацію через API.

### 4 — Прийом оплати та підтвердження

[Booking Engine](/uk/products/booking-engine/) виконує транзакцію — оформлення замовлення, оплату (Wink є продавцем), логіку політик скасування, підтвердження та синхронізацію бронювання з підключеним PMS або channel manager. Атрибуція джерела та партнера зберігається через бронювання.

### 5 — Реакція на події

Агент може підписатися на `booking.created` та інші webhook події, щоб узгоджувати, повідомляти мандрівника або запускати подальші дії.

Принцип: **агент створює або маршрутизує намір; Booking Engine залишається шаром виконання під кожною передачею.**

## AI пошук проти AI агентів

Вони вирішують різні завдання, і готель має бути готовим до обох.

| | AI пошук / пошукові системи відповідей | AI агенти |
|---|---|---|
| Мета мандрівника | Знайти та порівняти готелі | Забронювати та керувати перебуванням |
| Що потрібно готелю | [Структурований, доступний для сканування контент](/uk/resources/hotel-content-answer-engines/) | Живий API, тарифи, бронювання, оплата |
| Кінцевий результат | Рекомендація | Підтверджене бронювання |
| Поверхня Wink | Чисте постачання + контент, готовий для відповідей | REST API, MCP сервер, Booking Engine |

[AI відкриття для готелів](/uk/resources/ai-discovery-hotels/) охоплює пошукову сторону; цей посібник — транзакційну.

## Хто створює агентів для готельного комерційного сервісу

Агентський туристичний комерційний сервіс — це не лише споживчі асистенти. Та сама інфраструктура підтримує:

- **Споживчі туристичні асистенти**, які шукають, бронюють і керують перебуванням від початку до кінця.
- **Банківські, лояльні та супер-додатки агенти**, що вбудовують бронювання готелів у існуючий клієнтський досвід.
- **Партнерські та креаторські автоматизації**, які знаходять відповідні готелі, створюють активи та зберігають атрибуцію — заробляючи 10% стандартної комісії з підтверджених бронювань.
- **Копілоти на боці готелю**, які допомагають командам генерувати контент і аналізувати ефективність через [Extranet](/uk/products/extranet/), [Social](/uk/products/social/) та [Studio](/uk/products/studio/), поки готель контролює правила.

## Куди це рухається

Вищезазначені можливості вже доступні через REST API та MCP сервер. Напрямок — глибший агентський комерційний сервіс: багатші агентські примітиви бронювання, ідентифікація та авторизація агента для транзакцій від імені мандрівника, а також участь агентів як атрибутованих, що заробляють джерел у партнерській мережі. Спільна лінія — **інфраструктура туристичного комерційного сервісу для AI агентів**, з Booking Engine, що виконує транзакції під капотом.

## Поширені помилки

- **Вважати AI відкриття та AI агентів одним і тим самим проєктом.** Один — це контент і структура; інший — API та виконання. Потрібні обидва.
- **Дозволяти агентам називати ціни, які вони не можуть забронювати.** Ціни мають надходити з живих тарифів і наявності, а не зі скраплених сторінок.
- **Втрата атрибуції при передачі.** Якщо агент створює попит, бронювання має залишатися пов’язаним із цим джерелом.
- **Пропуск шару виконання.** Відповідь — це не бронювання, доки не відбувається оформлення, оплата та підтвердження.
