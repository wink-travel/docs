## Recommander un hôtel n’est pas le réserver

La plupart des « voyages IA » aujourd’hui s’arrêtent à la recommandation. Un assistant suggère trois hôtels, puis renvoie le voyageur vers un site web ou une OTA pour réserver réellement. Le fil se rompt, le prix peut ne pas être réservable, et personne ne conserve le contexte source.

Un **agent IA** est différent d’une réponse IA. Un agent ne se contente pas de décrire un hôtel — il agit : il vérifie la disponibilité en temps réel, assemble une réservation, prend le paiement, et peut réagir lorsqu’un changement survient. Pour que cela se passe en toute sécurité, l’agent a besoin de plus que du texte. Il a besoin de données structurées, actuelles et réservable, ainsi que d’une couche transactionnelle qu’il peut appeler.

C’est la différence entre la [découverte IA](/fr/resources/ai-discovery-hotels/), qui consiste à être **trouvé et compris**, et le commerce agentique, qui consiste à être **transacté**.

## Ce dont un agent a besoin avant de pouvoir transiger

Une réservation d’hôtel est un événement commercial réel : la bonne chambre, le bon tarif, une vraie disponibilité, des politiques, le paiement et une confirmation synchronisée avec l’hôtel. Un agent ne peut compléter cela que si chaque élément est disponible comme opération appelable.

| Ce dont l’agent a besoin | Pourquoi c’est important |
|---|---|
| Offre structurée et en direct | Les données extraites du web deviennent obsolètes ; un agent a besoin d’un inventaire actuel contrôlé par l’hôtel. |
| Tarifs et disponibilités en temps réel | Un prix cité par l’agent doit être réellement réservable à ce moment-là. |
| Une opération de réservation | La création de la réservation doit être un appel API réel, pas un transfert vers un formulaire web. |
| Paiement | L’agent (ou le voyageur via lui) doit pouvoir payer, avec la logique des politiques appliquée. |
| Attribution | La source, la campagne ou l’agent qui a créé la réservation doit rester attaché. |
| Événements | L’agent doit pouvoir réagir aux confirmations, changements, annulations et remboursements. |

Sans cela, un agent peut recommander — mais ne peut pas réserver.

## Comment un agent IA réserve un hôtel sur Wink

Wink est API-first : chaque fonctionnalité de la plateforme est appelable depuis l’extérieur, et un serveur MCP hébergé expose les contrats API en direct aux agents. Un flux d’agent typique :

### 1 — Se connecter et lire les contrats en direct

L’agent se connecte au serveur MCP hébergé et utilise `api_search` et `docs_search` pour trouver les bonnes opérations et lire leurs schémas de requête/réponse réels — pas de devinettes sur les endpoints, pas de docs obsolètes.

```bash
claude mcp add --transport http \
  wink-docs https://docs.mcp.wink.travel/mcp
```

### 2 — Rechercher l’inventaire réservable

L’agent recherche l’offre contrôlée par l’hôtel, y compris la recherche spatiale par géolocalisation, et consulte les tarifs et disponibilités en direct via les channel managers connectés.

### 3 — Créer la réservation

La création de réservation est une opération API REST. L’agent assemble la chambre, le tarif, les dates et les invités, et crée la réservation via l’API.

### 4 — Prendre le paiement et confirmer

[Booking Engine](/fr/products/booking-engine/) réalise la transaction — paiement, règlement (Wink est le marchand de référence), logique de politique d’annulation, confirmation, et synchronisation de la réservation avec le PMS ou channel manager connecté. L’attribution source et partenaire est conservée via la réservation.

### 5 — Réagir aux événements

L’agent peut s’abonner aux événements webhook `booking.created` et autres pour réconcilier, notifier le voyageur, ou déclencher des actions de suivi.

Le principe : **l’agent crée ou oriente l’intention ; Booking Engine reste la couche de réalisation sous chaque transfert.**

## Recherche IA vs agents IA

Ils résolvent des tâches différentes, et un hôtel doit être prêt pour les deux.

| | Recherche IA / moteurs de réponse | Agents IA |
|---|---|---|
| Objectif du voyageur | Trouver et comparer des hôtels | Réserver et gérer un séjour |
| Ce dont l’hôtel a besoin | [Contenu structuré et crawlable](/fr/resources/hotel-content-answer-engines/) | API en direct, tarifs, réservation, paiement |
| État final | Une recommandation | Une réservation confirmée |
| Surface Wink | Offre propre + contenu prêt pour réponse | API REST, serveur MCP, Booking Engine |

La [découverte IA pour les hôtels](/fr/resources/ai-discovery-hotels/) couvre le côté recherche ; ce guide couvre le côté transaction.

## Qui construit des agents sur le commerce hôtelier

Le commerce agentique dans le voyage ne concerne pas que les assistants consommateurs. La même infrastructure alimente :

- **Les assistants voyage consommateurs** qui recherchent, réservent et gèrent un séjour de bout en bout.
- **Les agents bancaires, fidélité et super-apps** intégrant la réservation d’hôtel dans une expérience client existante.
- **Les automatisations partenaires et créateurs** qui découvrent les hôtels éligibles, créent des assets et maintiennent l’attribution connectée — gagnant une commission par défaut de 10 % sur les réservations confirmées.
- **Les copilotes côté hôtel** qui aident les équipes à générer du contenu et analyser la performance sur [Extranet](/fr/products/extranet/), [Social](/fr/products/social/) et [Studio](/fr/products/studio/), tandis que l’hôtel garde la maîtrise des règles.

## Où cela va

Les capacités ci-dessus sont en production aujourd’hui via l’API REST et le serveur MCP. La direction est un commerce plus natif agent : primitives de réservation plus riches orientées agent, identité et autorisation agent pour transiger au nom du voyageur, et agents participant comme sources attribuées et rémunérées dans le réseau partenaire. Le fil conducteur est constant — **infrastructure de commerce de voyage pour agents IA**, avec Booking Engine réalisant en dessous.

## Erreurs courantes

- **Confondre découverte IA et agents IA comme un même projet.** L’un est contenu et structure ; l’autre est API et réalisation. Il faut les deux.
- **Laisser les agents citer des prix qu’ils ne peuvent pas réserver.** Les devis doivent provenir de tarifs et disponibilités en direct, pas de pages extraites.
- **Perdre l’attribution au transfert.** Si un agent crée la demande, la réservation doit rester connectée à cette source.
- **Sauter la couche de réalisation.** Une réponse n’est pas une réservation tant que le paiement, la confirmation et la finalisation n’ont pas eu lieu.
