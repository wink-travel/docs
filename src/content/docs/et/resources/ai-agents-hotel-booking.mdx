## Hotelli soovitamine ei ole broneerimine

Enamik tänapäevast "AI reisimist" lõpeb soovitusega. Assistent pakub kolme hotelli, seejärel suunab reisija veebisaidile või OTA-le, et tegelikult broneerida. Lõng katkeb, hind ei pruugi olla broneeritav ja keegi ei hoia allika konteksti.

**AI agent** erineb AI vastusest. Agent ei kirjelda ainult hotelli — ta tegutseb: kontrollib reaalajas saadavust, koostab broneeringu, võtab makse ja suudab muutustele reageerida. Selleks, et see toimiks turvaliselt, vajab agent rohkem kui teksti. Ta vajab struktureeritud, ajakohast ja broneeritavat andmestikku ning tehingukihti, mida saab kutsuda.

See on erinevus [AI avastamise](/et/resources/ai-discovery-hotels/) vahel, mis tähendab *leidmist ja mõistmist*, ning agentse kaubanduse vahel, mis tähendab *tehingute tegemist*.

## Mida agent vajab enne tehingu tegemist

Hotelli broneerimine on tõeline kaubanduslik sündmus: õige tuba, õige hind, reaalne saadavus, poliitikad, makse ja kinnitus, mis sünkroniseerub tagasi hotelliga. Agent saab selle lõpule viia ainult siis, kui iga osa on kättesaadav kutsutava toiminguna.

| Agent vajab | Miks see oluline on |
|---|---|
| Struktureeritud, reaalajas pakkumine | Veebist kraabitud andmed aeguvad; agent vajab ajakohast, hotelli kontrolli all olevat inventari. |
| Reaalajas hinnad ja saadavus | Agent poolt pakutav hind peab olema sellel hetkel tegelikult broneeritav. |
| Broneerimise toiming | Broneeringu loomine peab olema tõeline API kõne, mitte veebivormi suunamine. |
| Makse | Agent (või reisija tema kaudu) peab saama maksta, rakendades poliitikaloogikat. |
| Atribuutika | Broneeringu loonud allikas, kampaania või agent peaks jääma seotud. |
| Sündmused | Agent peaks suutma reageerida kinnitustele, muudatustele, tühistamistele ja tagasimaksetele. |

Ilma nendeta saab agent soovitada — kuid mitte broneerida.

## Kuidas AI agent broneerib hotelli Winkis

Wink on API-esmane: iga platvormi funktsioon on väljastpoolt kutsutav ja majutatud MCP server pakub agentidele reaalajas API lepinguid. Tüüpiline agendi töövoog:

### 1 — Ühenda ja loe reaalajas lepingud

Agent ühendub majutatud MCP serveriga ja kasutab `api_search` ja `docs_search`, et leida õiged toimingud ning lugeda nende tegelikke päringu/vastuse skeeme — pole vaja arvata lõpp-punkte ega kasutada aegunud dokumentatsiooni.

```bash
claude mcp add --transport http \
  wink-docs https://docs.mcp.wink.travel/mcp
```

### 2 — Otsi broneeritavat inventari

Agent otsib hotelli kontrolli all olevat pakkumist, sealhulgas geolokatsiooni ruumilist otsingut, ning loeb reaalajas hindu ja saadavust ühendatud kanalihaldurite kaudu.

### 3 — Loo broneering

Broneeringu loomine on REST API toiming. Agent koostab toa, hinna, kuupäevad ja külalised ning loob broneeringu API kaudu.

### 4 — Võta makse ja kinnita

[Booking Engine](/et/products/booking-engine/) täidab tehingu — väljaregistreerimine, makse (Wink on kaupmees), tühistamispoliitika loogika, kinnitus ja broneeringu sünkroonimine ühendatud PMS-i või kanalihalduriga. Allika ja partneri atribuutika säilib broneeringu kaudu.

### 5 — Reageeri sündmustele

Agent saab tellida `booking.created` ja teisi webhook sündmusi, et teha kokkuvõtteid, teavitada reisijat või käivitada järeltoiminguid.

Põhimõte: **agent loob või suunab kavatsuse; Booking Engine jääb täitmiskihtiks iga ülekande taga.**

## AI otsing vs AI agendid

Nad lahendavad erinevaid ülesandeid ja hotell peab olema valmis mõlemaks.

| | AI otsing / vastuse mootorid | AI agendid |
|---|---|---|
| Reisija eesmärk | Leida ja võrrelda hotelle | Broneerida ja hallata peatumist |
| Mida hotell vajab | [Struktureeritud, indekseeritav sisu](/et/resources/hotel-content-answer-engines/) | Reaalajas API, hinnad, broneerimine, makse |
| Lõpptulemus | Soovitus | Kinnitatud broneering |
| Wink pinnas | Puhas pakkumine + vastuseks valmis sisu | REST API, MCP server, Booking Engine |

[AI avastamine hotellide jaoks](/et/resources/ai-discovery-hotels/) käsitleb otsingut; see juhend käsitleb tehinguid.

## Kes ehitab agente hotellikauplemiseks

Agentne reisikaubandus ei ole ainult tarbijate assistendid. Sama infrastruktuur toetab:

- **Tarbijate reisijuhid**, kes otsivad, broneerivad ja haldavad peatumist algusest lõpuni.
- **Pangandus-, lojaalsus- ja superrakenduse agendid**, kes integreerivad hotelli broneerimise olemasolevasse kliendikogemusse.
- **Partnerite ja loojate automatiseerimised**, mis leiavad sobivaid hotelle, loovad materjale ja hoiavad atribuutika ühendatuna — teenides kinnitatud broneeringutelt 10% vaikimisi komisjonitasu.
- **Hotelli poolel olevad kaaspiloodid**, kes aitavad meeskondadel luua sisu ja analüüsida tulemuslikkust [Extranetis](/et/products/extranet/), [Socialis](/et/products/social/) ja [Studios](/et/products/studio/), samal ajal kui hotell hoiab reegleid.

## Kuhu see suundub

Ülaltoodud võimalused on tänapäeval reaalajas REST API ja MCP serveri kaudu. Suund on sügavam agentne kaubandus: rikkalikumad agendile suunatud broneerimisprimitiivid, agendi identiteet ja autoriseerimine reisija nimel tehingute tegemiseks ning agendid osalevad atribueeritud, tulu teenivate allikatena partnerivõrgustikus. Ühtne joon on järjepidev — **reisikaubanduse infrastruktuur AI agentidele**, kus Booking Engine täidab iga ülekande taga.

## Levinud vead

- **AI avastuse ja AI agentide käsitlemine samana projektina.** Üks on sisu ja struktuur; teine on API ja täitmine. Mõlemat on vaja.
- **Lubada agentidel pakkuda hindu, mida nad ei saa broneerida.** Pakkumised peavad tulema reaalajas hindadest ja saadavusest, mitte kraabitud lehtedelt.
- **Atribuutika kaotamine ülekande juures.** Kui agent loob nõudluse, peaks broneering jääma selle allikaga seotud.
- **Täitmiskihti vahele jätmine.** Vastus ei ole broneering, kuni väljaregistreerimine, makse ja kinnitus tegelikult toimuvad.
