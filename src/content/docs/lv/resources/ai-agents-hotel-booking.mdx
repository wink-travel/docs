## Ieteikt viesnīcu nav tas pats, kas to rezervēt

Lielākā daļa mūsdienu "AI ceļojumu" apstājas pie ieteikuma. Palīgs piedāvā trīs viesnīcas, pēc tam nodod ceļotāju uz vietni vai OTA, lai veiktu rezervāciju. Šis savienojums pārtrūkst, cena var nebūt rezervējama, un neviens nesaglabā avota kontekstu.

**AI aģents** atšķiras no AI atbildes. Aģents ne tikai apraksta viesnīcu — tas rīkojas: pārbauda tiešo pieejamību, veido rezervāciju, pieņem maksājumu un var reaģēt uz izmaiņām. Lai tas notiktu droši, aģentam vajag vairāk nekā tekstu. Tam nepieciešami strukturēti, aktuāli, rezervējami dati un darījumu slānis, ko var izsaukt.

Šī ir atšķirība starp [AI atklāšanu](/lv/resources/ai-discovery-hotels/), kas ir par **atrošanu un saprašanu**, un agentisko komerciju, kas ir par **darījumu veikšanu**.

## Kas aģentam nepieciešams, lai veiktu darījumu

Viesnīcas rezervācija ir reāls komerciāls notikums: pareizā istaba, pareizā cena, reāla pieejamība, noteikumi, maksājums un apstiprinājums, kas sinhronizējas ar viesnīcu. Aģents var to pabeigt tikai tad, ja katra daļa ir pieejama kā izsaucama operācija.

| Aģentam nepieciešams | Kāpēc tas ir svarīgi |
|---|---|
| Strukturēta, tieša piegāde | Tīmekļa skrāpētie dati noveco; aģentam vajag aktuālu, viesnīcas kontrolētu inventāru. |
| Reāllaika tarifi un pieejamība | Cena, ko aģents piedāvā, ir jābūt patiešām rezervējamai tajā brīdī. |
| Rezervēšanas operācija | Rezervācijas izveidei jābūt īstai API izsaukšanai, nevis nodošanai tīmekļa formai. |
| Maksājums | Aģentam (vai ceļotājam caur to) jāvar veikt maksājumu, piemērojot politikas loģiku. |
| Atribūcija | Avots, kampaņa vai aģents, kas izveidoja rezervāciju, jāpaliek piesaistītiem. |
| Notikumi | Aģentam jāspēj reaģēt uz apstiprinājumiem, izmaiņām, atcelšanām un atmaksām. |

Bez šiem aģents var ieteikt — bet nevar rezervēt.

## Kā AI aģents rezervē viesnīcu uz Wink

Wink ir API-pirmais: katra platformas funkcija ir izsaucama ārēji, un hostēts MCP serveris nodrošina tiešos API līgumus aģentiem. Tipisks aģenta darbplūsmas piemērs:

### 1 — Pieslēgties un lasīt tiešos līgumus

Aģents pieslēdzas hostētajam MCP serverim un izmanto `api_search` un `docs_search`, lai atrastu pareizās operācijas un izlasītu to reālos pieprasījuma/atbildes shēmas — bez minēšanas par galapunktiem, bez novecojušas dokumentācijas.

```bash
claude mcp add --transport http \
  wink-docs https://docs.mcp.wink.travel/mcp
```

### 2 — Meklēt rezervējamu inventāru

Aģents meklē viesnīcas kontrolētu piegādi, tostarp ģeolokācijas telpisko meklēšanu, un lasa tiešos tarifus un pieejamību caur savienotajiem kanālu pārvaldniekiem.

### 3 — Izveidot rezervāciju

Rezervācijas izveide ir REST API operācija. Aģents saliek istabu, tarifu, datumus un viesus un izveido rezervāciju caur API.

### 4 — Pieņemt maksājumu un apstiprināt

[Booking Engine](/lv/products/booking-engine/) izpilda darījumu — norēķini, maksājums (Wink ir reģistrētais tirgotājs), atcelšanas politikas loģika, apstiprinājums un rezervācijas sinhronizācija ar savienoto PMS vai kanālu pārvaldnieku. Avota un partnera atribūcija tiek saglabāta rezervācijā.

### 5 — Reaģēt uz notikumiem

Aģents var abonēt `booking.created` un citus webhook notikumus, lai saskaņotu, paziņotu ceļotājam vai aktivizētu turpmākas darbības.

Principā: **aģents izveido vai novirza nodomu; Booking Engine paliek kā izpildes slānis aiz katras nodošanas.**

## AI meklēšana pret AI aģentiem

Tie risina dažādus uzdevumus, un viesnīcai jābūt gatavai abiem.

| | AI meklēšana / atbilžu dzinēji | AI aģenti |
|---|---|---|
| Ceļotāja mērķis | Atrast un salīdzināt viesnīcas | Rezervēt un pārvaldīt uzturēšanos |
| Kas viesnīcai nepieciešams | [Strukturēts, indeksējams saturs](/lv/resources/hotel-content-answer-engines/) | Tiešs API, tarifi, rezervēšana, maksājums |
| Gala rezultāts | Ieteikums | Apstiprināta rezervācija |
| Wink virsma | Tīra piegāde + atbildēm gatavs saturs | REST API, MCP serveris, Booking Engine |

[AI atklāšana viesnīcām](/lv/resources/ai-discovery-hotels/) aptver meklēšanas pusi; šis ceļvedis aptver darījumu pusi.

## Kas veido aģentus viesnīcu komercijā

Agentiska ceļojumu komercija nav tikai patērētāju palīgi. Tā paša infrastruktūra nodrošina:

- **Patērētāju ceļojumu palīgus**, kas meklē, rezervē un pārvalda uzturēšanos no sākuma līdz beigām.
- **Banku, lojalitātes un super-app aģentus**, kas integrē viesnīcu rezervēšanu esošā klientu pieredzē.
- **Partneru un veidotāju automatizācijas**, kas atrod piemērotas viesnīcas, veido materiālus un saglabā atribūciju — nopelnot 10% noklusējuma komisiju no apstiprinātām rezervācijām.
- **Viesnīcas puses kopilotus**, kas palīdz komandām ģenerēt saturu un analizēt veiktspēju caur [Extranet](/lv/products/extranet/), [Social](/lv/products/social/) un [Studio](/lv/products/studio/), kamēr viesnīca saglabā noteikumus.

## Uz kurieni tas virzās

Iepriekš minētās iespējas jau darbojas caur REST API un MCP serveri. Virziens ir dziļāka aģentiem draudzīga komercija: bagātīgāki aģentiem paredzēti rezervēšanas primitīvi, aģenta identitāte un autorizācija darījumu veikšanai ceļotāja vārdā, un aģenti kā piesaistīti, pelnoši avoti partneru tīklā. Kopējā līnija ir konsekventa — **ceļojumu komercijas infrastruktūra AI aģentiem**, ar Booking Engine kā izpildes slāni.

## Biežas kļūdas

- **AI atklāšanu un AI aģentus uzskatīt par vienu un to pašu projektu.** Viens ir saturs un struktūra; otrs ir API un izpilde. Vajag abus.
- **Ļaut aģentiem piedāvāt cenas, ko nevar rezervēt.** Piedāvājumiem jābūt no tiešajiem tarifiem un pieejamības, nevis no skrāpētiem lapu datiem.
- **Pazaudēt atribūciju nodošanas brīdī.** Ja aģents rada pieprasījumu, rezervācijai jāpaliek piesaistītai tam avotam.
- **Izlaist izpildes slāni.** Atbilde nav rezervācija, kamēr nenotiek norēķins, maksājums un apstiprinājums.
