## Att rekommendera ett hotell är inte att boka ett

De flesta "AI-resor" idag stannar vid rekommendationen. En assistent föreslår tre hotell och skickar sedan vidare resenären till en webbplats eller OTA för att faktiskt boka. Tråden bryts, priset kanske inte går att boka, och ingen behåller källkontexten.

En **AI-agent** skiljer sig från ett AI-svar. En agent beskriver inte bara ett hotell — den agerar: kontrollerar live-tillgänglighet, sätter ihop en bokning, tar betalt och kan reagera när något ändras. För att det ska ske säkert behöver agenten mer än text. Den behöver strukturerad, aktuell, bokningsbar data och ett transaktionslager den kan anropa.

Detta är skillnaden mellan [AI-upptäckt](/sv/resources/ai-discovery-hotels/), som handlar om att bli **hittad och förstådd**, och agentisk handel, som handlar om att bli **transakterad**.

## Vad en agent behöver innan den kan transaktera

En hotellbokning är en verklig kommersiell händelse: rätt rum, rätt pris, verklig tillgänglighet, policyer, betalning och en bekräftelse som synkroniseras tillbaka till hotellet. En agent kan bara slutföra detta om varje del finns som en anropbar operation.

| Agenten behöver | Varför det är viktigt |
|---|---|
| Strukturerad, live-tillgång | Webbscrapad data blir snabbt inaktuell; en agent behöver aktuell, hotellkontrollerad inventarie. |
| Realtidspriser & tillgänglighet | Ett pris som agenten anger måste faktiskt gå att boka just då. |
| En bokningsoperation | Att skapa reservationen måste vara ett riktigt API-anrop, inte en överlämning till ett webbformulär. |
| Betalning | Agenten (eller resenären via den) måste kunna betala, med policylogik tillämpad. |
| Attribution | Källan, kampanjen eller agenten som skapade bokningen ska förbli kopplad. |
| Händelser | Agenten ska kunna reagera på bekräftelser, ändringar, avbokningar och återbetalningar. |

Utan detta kan en agent rekommendera — men inte boka.

## Hur en AI-agent bokar hotell på Wink

Wink är API-först: varje plattformsfunktion är anropbar externt, och en hostad MCP-server exponerar live API-kontrakt till agenter. Ett typiskt agentflöde:

### 1 — Anslut och läs live-kontrakten

Agenten ansluter till den hostade MCP-servern och använder `api_search` och `docs_search` för att hitta rätt operationer och läsa deras verkliga förfrågnings-/svars-scheman — inget gissande på endpoints, inga inaktuella dokument.

```bash
claude mcp add --transport http \
  wink-docs https://docs.mcp.wink.travel/mcp
```

### 2 — Sök bokningsbar inventarie

Agenten söker hotellkontrollerad tillgång, inklusive geolokaliserad rumsökning, och läser livepriser och tillgänglighet över anslutna channel managers.

### 3 — Skapa bokningen

Bokningsskapande är en REST API-operation. Agenten sätter ihop rum, pris, datum och gäster och skapar reservationen via API:et.

### 4 — Ta betalt och bekräfta

[Booking Engine](/sv/products/booking-engine/) fullgör transaktionen — utcheckning, betalning (Wink är betalningsmottagare), avbokningspolicylogik, bekräftelse och bokningssynk till ansluten PMS eller channel manager. Källa och partnerattribution bevaras genom bokningen.

### 5 — Reagera på händelser

Agenten kan prenumerera på `booking.created` och andra webhook-händelser för att stämma av, meddela resenären eller trigga uppföljningsåtgärder.

Principen: **agenten skapar eller dirigerar avsikt; Booking Engine förblir fullgörandelagret under varje överlämning.**

## AI-sökning vs AI-agenter

De löser olika uppgifter, och ett hotell behöver vara redo för båda.

| | AI-sökning / svarsmotorer | AI-agenter |
|---|---|---|
| Resenärens mål | Hitta och jämföra hotell | Boka och hantera en vistelse |
| Vad hotellet behöver | [Strukturerat, genomsökningsbart innehåll](/sv/resources/hotel-content-answer-engines/) | Live-API, priser, bokning, betalning |
| Slutresultat | En rekommendation | En bekräftad bokning |
| Wink-yta | Ren tillgång + svarsklart innehåll | REST API, MCP-server, Booking Engine |

[AI-upptäckt för hotell](/sv/resources/ai-discovery-hotels/) täcker söksidan; denna guide täcker transaktionssidan.

## Vem bygger agenter för hotellhandel

Agentisk resehandel är inte bara konsumentassistenter. Samma infrastruktur driver:

- **Konsumentresassistenter** som söker, bokar och hanterar en vistelse från början till slut.
- **Bank-, lojalitets- och superapp-agenter** som integrerar hotellbokning i en befintlig kundupplevelse.
- **Partner- och skapareautomationer** som hittar berättigade hotell, bygger tillgångar och håller attribution kopplad — och tjänar 10 % standardprovision på bekräftade bokningar.
- **Hotellsidans copiloter** som hjälper team att skapa innehåll och analysera prestanda över [Extranet](/sv/products/extranet/), [Social](/sv/products/social/) och [Studio](/sv/products/studio/), medan hotellet behåller reglerna.

## Vart detta är på väg

Funktionerna ovan är live idag via REST API och MCP-server. Riktningen är djupare agent-native handel: rikare agentinriktade bokningsprimitiver, agentidentitet och auktorisering för att transaktera på resenärens vägnar, och agenter som deltar som attribuerade, intjänande källor i partnernätverket. Den röda tråden är konsekvent — **resehandelsinfrastruktur för AI-agenter**, med Booking Engine som fullgörare under.

## Vanliga misstag

- **Att behandla AI-upptäckt och AI-agenter som samma projekt.** Det ena är innehåll och struktur; det andra är API och fullgörande. Du behöver båda.
- **Att låta agenter ange priser de inte kan boka.** Priser måste komma från livepriser och tillgänglighet, inte från scrappade sidor.
- **Att tappa attribution vid överlämning.** Om en agent skapar efterfrågan ska bokningen förbli kopplad till den källan.
- **Att hoppa över fullgörandelagret.** Ett svar är inte en bokning förrän utcheckning, betalning och bekräftelse faktiskt sker.
