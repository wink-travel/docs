## 推薦飯店不等於訂房

現今大多數「AI 旅遊」止於推薦。助理建議三家飯店，然後將旅客交給網站或 OTA 實際訂房。流程中斷，價格可能無法訂購，且沒有人保留來源上下文。

**AI agent** 與 AI 答案不同。agent 不只是描述飯店 — 它會行動：檢查即時可用性、組合訂單、收款，並能在狀況改變時回應。為了安全執行，agent 需要的不只是文字，而是結構化、即時且可訂購的資料，以及可呼叫的交易層。

這是 [AI 發現](/zh-TW/resources/ai-discovery-hotels/)（關於被**找到與理解**）與代理式商務（關於被**交易**）的差異。

## agent 交易前需要什麼

飯店訂房是一個真實的商業事件：正確的房型、正確的價格、真實的可用性、政策、付款與同步回飯店的確認。agent 只有在每個環節都能作為可呼叫操作時，才能完成訂單。

| agent 需要 | 重要原因 |
|---|---|
| 結構化、即時供應 | 網頁爬蟲資料會過時；agent 需要即時、飯店控制的庫存。 |
| 即時價格與可用性 | agent 報價必須是當下可訂購的價格。 |
| 訂房操作 | 建立訂單必須是真正的 API 呼叫，而非轉交網頁表單。 |
| 付款 | agent（或旅客透過 agent）必須能付款，並套用政策邏輯。 |
| 歸因 | 建立訂單的來源、活動或 agent 應保留關聯。 |
| 事件 | agent 應能回應確認、變更、取消與退款等事件。 |

沒有這些，agent 只能推薦，無法訂房。

## AI agent 如何在 Wink 訂房

Wink 採用 API 優先：每個平台功能都可外部呼叫，且託管的 MCP 伺服器向 agents 開放即時 API 合約。典型 agent 流程：

### 1 — 連接並讀取即時合約

agent 連接託管的 MCP 伺服器，使用 `api_search` 和 `docs_search` 找到正確操作並讀取其真實請求/回應結構 — 不用猜測端點，也不會讀到過時文件。

```bash
claude mcp add --transport http \
  wink-docs https://docs.mcp.wink.travel/mcp
```

### 2 — 搜尋可訂購庫存

agent 搜尋飯店控制的供應，包括地理位置空間搜尋，並讀取連接的渠道管理系統的即時價格與可用性。

### 3 — 建立訂單

訂房建立是 REST API 操作。agent 組合房型、價格、日期與旅客，並透過 API 建立訂單。

### 4 — 收款並確認

[Booking Engine](/zh-TW/products/booking-engine/) 履約交易 — 結帳、付款（Wink 為商戶）、取消政策邏輯、確認與訂單同步至連接的 PMS 或渠道管理系統。訂單保留來源與合作夥伴歸因。

### 5 — 回應事件

agent 可訂閱 `booking.created` 等 webhook 事件以進行對帳、通知旅客或觸發後續動作。

原則：**agent 建立或導向意圖；Booking Engine 始終是每次交接背後的履約層。**

## AI 搜尋 vs AI agents

它們解決不同任務，飯店需同時準備。

| | AI 搜尋 / 答案引擎 | AI agents |
|---|---|---|
| 旅客目標 | 找到並比較飯店 | 訂房並管理住宿 |
| 飯店需求 | [結構化、可爬取內容](/zh-TW/resources/hotel-content-answer-engines/) | 即時 API、價格、訂房、付款 |
| 最終狀態 | 推薦 | 確認訂單 |
| Wink 介面 | 清潔供應 + 答案準備內容 | REST API、MCP 伺服器、Booking Engine |

[AI 發現飯店](/zh-TW/resources/ai-discovery-hotels/) 涵蓋搜尋面；本指南涵蓋交易面。

## 誰在飯店商務上打造 agents

代理式旅遊商務不僅是消費者助理。相同基礎設施支持：

- **消費者旅遊助理**，端到端搜尋、訂房與管理住宿。
- **銀行、忠誠度與超級應用 agents**，將飯店訂房嵌入現有客戶體驗。
- **合作夥伴與創作者自動化**，發現合格飯店、建立資產並保持歸因連結 — 確認訂單可獲 10% 預設佣金。
- **飯店端輔助工具**，協助團隊在 [Extranet](/zh-TW/products/extranet/)、[Social](/zh-TW/products/social/) 與 [Studio](/zh-TW/products/studio/) 產生內容與分析績效，同時飯店掌控規則。

## 未來趨勢

上述功能已透過 REST API 與 MCP 伺服器實現。未來方向是更深度的 agent 原生商務：更豐富的 agent 面向訂房原語、agent 身份與授權以代表旅客交易，agent 作為合作夥伴網絡中有歸因且能賺取收益的來源。核心是一致的 — **為 AI agents 提供旅遊商務基礎設施**，由 Booking Engine 履約。

## 常見錯誤

- **將 AI 發現與 AI agents 視為同一專案。** 一個是內容與結構，另一個是 API 與履約。兩者皆需。
- **讓 agents 報價卻無法訂購。** 報價必須來自即時價格與可用性，而非爬蟲頁面。
- **交接時丟失歸因。** 若 agent 創造需求，訂單應保留該來源關聯。
- **跳過履約層。** 答案不是訂單，直到結帳、付款與確認完成。
