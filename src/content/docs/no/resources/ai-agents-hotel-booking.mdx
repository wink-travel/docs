## Å anbefale et hotell er ikke det samme som å bestille ett

Det meste av "AI-reiser" i dag stopper ved anbefalingen. En assistent foreslår tre hoteller, og sender deretter den reisende videre til et nettsted eller en OTA for å faktisk bestille. Tråden brytes, prisen kan være umulig å bestille, og ingen beholder kildekonteksten.

En **AI-agent** er annerledes enn et AI-svar. En agent beskriver ikke bare et hotell — den handler: den sjekker live tilgjengelighet, setter sammen en bestilling, tar betaling og kan reagere når noe endres. For at dette skal skje trygt, trenger agenten mer enn tekst. Den trenger strukturert, oppdatert, bestillbar data og et transaksjonslag den kan kalle.

Dette er forskjellen mellom [AI-discovery](/no/resources/ai-discovery-hotels/), som handler om å bli **funnet og forstått**, og agentisk handel, som handler om å bli **transaktert**.

## Hva en agent trenger før den kan gjennomføre en transaksjon

En hotellbestilling er en reell kommersiell hendelse: riktig rom, riktig pris, reell tilgjengelighet, regler, betaling og en bekreftelse som synkroniseres tilbake til hotellet. En agent kan bare fullføre dette hvis hver del er tilgjengelig som en kallbar operasjon.

| Agenten trenger | Hvorfor det er viktig |
|---|---|
| Strukturert, live tilbud | Webskrapet data blir utdatert; en agent trenger oppdatert, hotellstyrt inventar. |
| Sanntidspriser og tilgjengelighet | En pris agenten oppgir må faktisk kunne bestilles i det øyeblikket. |
| En bookingoperasjon | Opprettelse av reservasjonen må være et ekte API-kall, ikke en overføring til et webskjema. |
| Betaling | Agenten (eller den reisende gjennom den) må kunne betale, med regelverk anvendt. |
| Attribusjon | Kilden, kampanjen eller agenten som opprettet bestillingen bør forbli knyttet. |
| Hendelser | Agenten bør kunne reagere på bekreftelser, endringer, kanselleringer og refusjoner. |

Uten dette kan en agent anbefale — men ikke bestille.

## Hvordan en AI-agent bestiller et hotell på Wink

Wink er API-først: hver plattformfunksjon kan kalles eksternt, og en hostet MCP-server eksponerer de levende API-kontraktene til agenter. En typisk agentflyt:

### 1 — Koble til og les de levende kontraktene

Agenten kobler til den hostede MCP-serveren og bruker `api_search` og `docs_search` for å finne riktige operasjoner og lese deres faktiske forespørsels-/responsskjemaer — ingen gjetting på endepunkter, ingen utdaterte dokumenter.

```bash
claude mcp add --transport http \
  wink-docs https://docs.mcp.wink.travel/mcp
```

### 2 — Søk i bestillbart inventar

Agenten søker i hotellstyrt tilbud, inkludert geolokasjonsbasert søk, og leser live priser og tilgjengelighet på tvers av tilkoblede channel managere.

### 3 — Opprett bestillingen

Opprettelse av bestilling er en REST API-operasjon. Agenten setter sammen rom, pris, datoer og gjester, og oppretter reservasjonen via API-et.

### 4 — Ta betaling og bekreft

[Booking Engine](/no/products/booking-engine/) utfører transaksjonen — utsjekk, betaling (Wink er registrert som selger), kanselleringsregler, bekreftelse og synkronisering av bestillingen til tilknyttet PMS eller channel manager. Kilde- og partnerattribusjon bevares gjennom bestillingen.

### 5 — Reager på hendelser

Agenten kan abonnere på `booking.created` og andre webhook-hendelser for å avstemme, varsle den reisende eller utløse oppfølgingshandlinger.

Prinsippet: **agenten oppretter eller ruter intensjon; Booking Engine forblir oppfyllingslaget under hver overlevering.**

## AI-søk vs AI-agenter

De løser forskjellige oppgaver, og et hotell må være klart for begge.

| | AI-søk / svarmotorer | AI-agenter |
|---|---|---|
| Reisendes mål | Finne og sammenligne hoteller | Bestille og administrere et opphold |
| Hva hotellet trenger | [Strukturert, indekserbart innhold](/no/resources/hotel-content-answer-engines/) | Live API, priser, booking, betaling |
| Sluttresultat | En anbefaling | En bekreftet bestilling |
| Wink-grensesnitt | Rent tilbud + svarklart innhold | REST API, MCP-server, Booking Engine |

[AI-discovery for hoteller](/no/resources/ai-discovery-hotels/) dekker søkesiden; denne guiden dekker transaksjonssiden.

## Hvem bygger agenter for hotellhandel

Agentisk reisehandel er ikke bare for forbrukerassistenter. Samme infrastruktur driver:

- **Forbrukerreiseassistenter** som søker, bestiller og administrerer et opphold fra start til slutt.
- **Bank-, lojalitets- og superapp-agenter** som integrerer hotellbestilling i en eksisterende kundeopplevelse.
- **Partner- og skaperautomatiseringer** som oppdager kvalifiserte hoteller, bygger eiendeler og holder attribusjon koblet — og tjener 10 % standard provisjon på bekreftede bestillinger.
- **Hotellbaserte copiloter** som hjelper team med å generere innhold og analysere ytelse på tvers av [Extranet](/no/products/extranet/), [Social](/no/products/social/) og [Studio](/no/products/studio/), mens hotellet beholder reglene.

## Hvor dette er på vei

Kapasitetene ovenfor er live i dag gjennom REST API og MCP-server. Retningen er dypere agent-native handel: rikere agentrettede bookingprimitiver, agentidentitet og autorisasjon for å transaktere på vegne av en reisende, og agenter som deltar som attribuerte, inntektsbringende kilder i partnernettverket. Gjennomgangen er konsistent — **reisehandelsinfrastruktur for AI-agenter**, med Booking Engine som oppfyller under.

## Vanlige feil

- **Å behandle AI-discovery og AI-agenter som samme prosjekt.** Det ene er innhold og struktur; det andre er API og oppfyllelse. Du trenger begge.
- **Å la agenter oppgi priser de ikke kan bestille.** Tilbud må komme fra live priser og tilgjengelighet, ikke skrapede sider.
- **Å miste attribusjon ved overlevering.** Hvis en agent skaper etterspørsel, bør bestillingen forbli knyttet til den kilden.
- **Å hoppe over oppfyllingslaget.** Et svar er ikke en bestilling før utsjekk, betaling og bekreftelse faktisk skjer.
